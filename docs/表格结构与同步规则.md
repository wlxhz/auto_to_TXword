# 表格结构与同步规则

## 结构来源

结构依据：`服务器血糖客户汇总_2026-09-22.xlsx`。

- 工作表：`血糖客户汇总`
- 表头行：第 1 行
- 数据区：第 2 行开始
- 总列数：15
- 日期显示格式：`yyyy-mm-dd`
- 血糖列显示格式：`0.00`
- 源工作簿没有公式；更新版在 H:K 列新增依赖 G 列的日期公式，修改佩戴日期后可自动重算。

线上同步方案需要在这 15 列之外增加两个**文本**字段：“客户ID”（数据库 UUID）和“最近更新日期”（`yyyy-mm-dd`）。当前提供的腾讯文档链接为 `/sheet/` 普通在线表格，尚未完成线上字段核查或写入，因此以下为目标规则，不代表线上已生效。

## 字段所有权

| 列 | 字段 | 当前状态 | 自动化权限 |
|---:|---|---|---|
| A | 序号 | 已填写 | 审查并更新 |
| B | 姓名 | 已填写 | UUID 已回填后可审查并更新；旧行迁移时用于匹配 |
| C | 性别 | 当前为空 | 不读取、不覆盖 |
| D | 电话 | 当前为空 | 服务器有值时审查并更新；缺失时保留已有值 |
| E | 是否是糖尿病 | 当前为空 | 不读取、不覆盖 |
| F | 是否服药 | 当前为空 | 不读取、不覆盖 |
| G | 首次佩戴日期 | 已填写 | UUID 已回填后可审查并更新；旧行迁移时用于匹配 |
| H | 1小时回访 | 已补计划日期 | 首次佩戴当天（+0 天） |
| I | 3天回访 | 已补计划日期 | 首次佩戴 +3 天 |
| J | 首次周回访 | 已补计划日期 | 首次佩戴 +9 天 |
| K | 取机器回访 | 已补计划日期 | 首次佩戴 +13 天 |
| L | 血糖均值 | 已填写 | 审查并更新 |
| M | 血糖最高值 | 已填写 | 审查并更新 |
| N | 血糖最低值 | 已填写 | 审查并更新 |
| O | 14天血糖达标情况 | 当前为空 | 不读取、不覆盖 |

“当前为空”描述的是原结构参考文件的状态。H:K 现在定义为计划日期，而非实际完成记录或回访备注；实际执行情况应另设列记录，避免计划值覆盖人工记录。

源表“姓名”列中存在看起来像手机号或内部编号的文本，而“电话”列仍为空。自动化不会猜测这些值就是电话；必须由服务器 `phone` 字段或人工核实后补入。

例如首次佩戴 `2026-10-01`，四个计划日期依次为 `2026-10-01`、`2026-10-04`、`2026-10-10`、`2026-10-14`。其中“1小时回访”列仅存**日期**，不存精确到小时的时间；首次佩戴的具体时刻未提供。

本地 Excel 版本在 H:K 数据区使用条件格式：`AND(ISNUMBER(H2),INT(H2)=TODAY())`，逐格相对应用。只要计划日期等于系统日期，就显示红色字体。线上四个字段均为文本，计划日期采用 `yyyy-mm-dd`；需使用目标表格支持的文本条件格式或其他经验证的格式接口，不能直接沿用 Excel 数值日期公式。每日脚本另以北京时间统计四类今日应回访数量。

## 记录匹配

主键采用数据库 `customers.id` UUID，对应腾讯表格的“客户ID”列。旧行若尚无 ID，迁移时暂用以下组合键：

```text
姓名 + 首次佩戴日期
```

匹配前会：

- 去掉首尾和重复空格。
- 统一全角/半角字符。
- 忽略大小写差异。
- 移除零宽字符，避免看起来相同的姓名无法匹配。
- 将毫秒时间戳和 ISO 日期统一成北京时间日期；配置项 `date_timezone_offset_hours` 默认为 `8`。

旧组合键重复时不猜测目标行，任务直接失败并通知工作人员。UUID 回填后按 UUID 匹配，不依赖可能改名或重复的姓名。

## 监测期与置顶

- 首次佩戴当天为第 1 天，直到第 14 天结束均可同步；第 15 天开始不再改动该行。
- 监测期内出现的数据库新客户可新增行，不覆盖已有客户。
- 某行当日有业务字段变化或新建时，写“最近更新日期”为当天；仅序号变化或旧行补客户 ID 不触发置顶。
- 将“最近更新日期”按文本降序排序，`yyyy-mm-dd` 格式可使当天更新的行排在前面。排序视图需在实际目标表格中配置并验证。

## 差异判定

- 数值按数值比较，不因 `6.3` 与 `6.30` 的显示差异触发更新。
- 文本规范化后比较。
- 服务器空值默认视为“本次没有可用更新”，不会清空文档值。
- 主键字段不通过日常审查流程改写。
- 更新请求只包含实际变化的字段，不发送完整行。

## 审查结果

每次运行输出以下计数：

- `source_records`：服务器记录数。
- `target_records`：腾讯文档记录数。
- `updated`：实际提交更新的记录数。
- `unchanged`：匹配且没有变化的记录数。
- `added`：自动新增记录数，默认应为 0。
- `unmatched_source`：服务器存在、腾讯文档不存在的记录数。
- `unmatched_target`：腾讯文档存在、服务器不存在的记录数。
- `changed_fields`：各字段发生变化的次数。

日志和通知不输出客户姓名、手机号或血糖明细。

## 医疗数据边界

自动化只负责数据一致性，不做医学判断：

- 不自行设定正常血糖范围。
- 不根据单次均值、最高值或最低值诊断疾病。
- 不自动填写“是否是糖尿病”“是否服药”或“14天血糖达标情况”。
- 若以后增加达标判断，必须先取得明确的业务协议、单位、目标范围和适用人群规则，再单独配置与审核。

## 建议的后续结构改进

数据库已有稳定的 `customers.id` UUID；目标表格应新增“客户ID”文本列用于匹配。若同一客户今后会进行第二个独立的 14 天佩戴周期，需要在数据库增加“佩戴周期/监测记录 ID”，届时以该 ID 区分两轮监测，避免旧客户的新周期被当前 14 天冻结规则跳过。
